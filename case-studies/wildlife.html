Code & architecture

Wildlife Detection API

An image-inference API architecture combining YOLOv8, FastAPI and container deployment. The repository documents validation, readiness probes and infrastructure configuration.

No published wildlife mAP or reproducible latency result. Not featured as a measured outcome.

Data flow and architecture

Architecture follows the repository documentation. No current public endpoint is verified.

  1. Submitted image
  2. FastAPI request validation
  3. Decode and resize
  4. YOLOv8 / ONNX inference
  5. JSON detections or annotated image
  6. Kubernetes health and readiness probes

Why this project

An image model needs an API, validation and a deployment path before another application can use it. This repository explores that surrounding engineering.

What went wrong

The architecture is documented, but there is no published wildlife accuracy benchmark or reproducible latency result. Deployment configuration alone does not establish model quality.

What I’d do differently

I'd start with a labelled wildlife evaluation set and publish precision, recall and latency before spending more time on infrastructure.

Failure and limitations

Readiness checks prevent traffic before model startup. ONNX has a PyTorch fallback. Task-specific accuracy and overload behaviour still need evaluation.

Scale and evaluation

Replica configuration and Locust tooling are documented; a completed load-test result is not supplied.

Hosting and cost

OCI compute and Kubernetes hosting would require provisioning and a separate cost estimate. No running cloud cost is claimed.

Security and privacy

Authentication, rate limiting, scanning and production observability are listed as future work in the repository.

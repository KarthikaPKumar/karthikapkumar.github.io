Why this project

Batteries gave this project a practical question: can we forecast capacity loss early enough to make the next measurement less of a surprise? The appeal is that a prediction can be checked against real measurements and a simple baseline. This is a small laboratory study, not a vehicle-ready model.

What went wrong

The main risk is an easy evaluation. Neighbouring windows from the same cell share history, so a random row split can make the model look better than it is. This pipeline holds out whole batteries. That still leaves only four laboratory cells, not evidence of performance on vehicles.

What I’d do differently

I'd test on more cells and different operating conditions before adding model complexity. I'd also check how error changes as the forecast horizon grows, rather than reporting one average.

Failure and limitations

Cell-level holdout limits leakage between training and evaluation. Data checks reject invalid forecast populations. Four laboratory cells do not establish vehicle-fleet reliability.

Scale and evaluation

Four cells and 560 held-out forecast windows. No production throughput or latency benchmark is claimed.

Hosting and cost

The public dashboard is static. Running the local model and agent uses your own computer; no hosted LLM service is required.

Security and privacy

The local agent exposes bounded read-only metric tools, not arbitrary SQL, shell access or data writes.

Payments fraud data platform · 2026

Nexora

A payments fraud platform that streams events into an Iceberg lakehouse, transforms them through 28 tested dbt models and explains LightGBM alerts in a Streamlit console.

Recall 0.97 vs 0.45 for SQL rules at equal alert volume · synthetic data

Data flow and architecture

Data engineering and fraud modelling project, evaluated on synthetic payments with time-based validation and three seeds.

  1. Kafka payment events
  2. Data contracts and quarantine
  3. Apache Iceberg lakehouse with idempotent reloads
  4. 28 dbt models and quality tests
  5. Airflow orchestration + GitHub Actions CI
  6. LightGBM graph features + SHAP in Streamlit

Why this project

A useful fraud model needs dependable event ingestion, reproducible transformations and explanations an investigator can inspect.

What went wrong

Invalid events and repeated loads can undermine downstream fraud features. Contracts, quarantine, idempotent reloads and dbt tests make those failure modes explicit.

What I’d do differently

Evaluate on representative, appropriately governed payment data and monitor drift, alert quality and operational cost. The existing public DataMedic demo is a separate incident-diagnosis project, not this fraud evaluation. Earlier incident-diagnosis demo: https://karthikapkumar.github.io/Nexora-demo/

Failure and limitations

Synthetic-data recall is not evidence of performance on real payments. Time-based validation and equal alert volume make the model–rules comparison meaningful within this evaluation.

Scale and evaluation

28 dbt models. LightGBM with graph features achieved recall 0.97 versus 0.45 for SQL rules at the same alert volume across a three-seed evaluation.

Hosting and cost

No production hosting-cost or throughput benchmark is claimed.

Security and privacy

Data contracts and quarantine isolate invalid events; evaluation uses synthetic payment data.
